# Session Notes — 2026-07-01

## Context

The goal is to design architecture for embedding Centaur inside `pacta-web` as a Pacta workspace agent.

This should behave more like a dashboard / control plane than a browser IDE.

Centaur should be able to work on real repositories, but human approvals must exist at sensitive transitions.

## Original Working Metaphor

The architecture is being explored using three concepts:

- `center`
- `shell`
- `rails`

The design should remain iterative and collaborative.

## What Was Rejected

A first interpretation treated the center as a task runtime responsible for things like planning a ticket or applying a change.

That framing was rejected because those actions are not the core architectural idea. Any AI can do that. The value here is not "an AI that performs tasks", but a system architecture where AI participates in a controlled and adaptable way.

## Current Interpretation

### Center

The center is not the full system and not just "the AI".

It is closer to an orchestration / adaptation layer:

- helps manage the architecture
- can assist the monolith process
- can coordinate existing capabilities
- can connect extra systems later
- can use memory systems later
- can accelerate or slow down processes
- can adapt behavior according to current needs

The center should not automatically become the unrestricted brain of the whole platform.

### Shell

The shell is the monolithic structural body.

It contains the stable architectural pieces that many systems share, even if they are arranged differently:

- APIs
- models
- calls between parts
- application structure
- architectural organization of capabilities

Persistence was intentionally set aside for now.

Memory was also put aside temporarily, even though it may eventually live near the shell as a subsystem.

### Rails

The rails are not "free access" and not merely ticket workflow commands.

They are the controlled movement mechanisms that let the architecture behave more like a Rubik's cube:

- routes for controlled action
- ways the center can move, influence, or coordinate the system
- support for changing how parts interact without dissolving boundaries

The rails still need sharper definition.

## Important Shift in Framing

The architecture is not being approached as:

- AI as the product
- AI as the whole runtime
- AI replacing architecture

It is being approached as:

- architecture first
- AI as orchestrator / helper / adaptation layer
- strong interest in controlled paths rather than open-ended access

## Architectural Learning Goal

Before defining the rails precisely, the next learning goal is to understand architecture families:

- what kinds exist
- what each one does
- how each one is arranged
- what each one is for

The focus is specifically on vanilla programming architecture, not yet on infrastructure-heavy concerns.

## Working Distinctions Introduced

These distinctions were introduced to make the landscape easier to reason about:

- `monolith / microservices` describe high-level system separation and deployment shape
- `layers / hexagonal / clean` describe internal code organization and dependency direction
- `features / modules` describe how responsibilities are grouped
- `events / workflows / pipelines` describe how behavior moves through the system

## Architecture Families Mentioned

The discussion introduced these families as a practical map, not as an exhaustive taxonomy:

### Monolith

A single application / process containing the system.

Useful for:

- centralized products
- fast development
- simpler operational control

Risk:

- everything can collapse into everything talking to everything

### Modular Monolith

A monolith with explicit internal boundaries.

Useful for:

- keeping operational simplicity
- improving internal order
- scaling complexity without defaulting to microservices

This currently appears close to the intended direction, but it is not a final decision.

### Layered Architecture

Organizes code by levels such as presentation, application, domain, infrastructure.

Useful for:

- separating user interaction, business rules, and technical integration

Risk:

- too much ceremony if layers add no real separation

### Hexagonal / Ports and Adapters

Protects the core logic from external tools and frameworks through defined interfaces.

Useful for:

- isolating business logic
- swapping integrations
- controlling external access

### Clean Architecture

Similar to hexagonal, with strong emphasis on inward dependency direction.

Useful for:

- protecting central rules
- preventing frameworks from driving the design

Risk:

- easy to overdesign

### Feature-Oriented Architecture

Organizes code around product capabilities instead of technical buckets.

Useful for:

- reflecting the actual product surface
- reducing cross-folder mental overhead

### Event-Driven Internal Architecture

Parts react to events rather than only using direct calls.

Useful for:

- decoupling
- extensibility
- action history

Risk:

- harder to trace if overused

### Pipeline / Workflow-Oriented Design

Represents work as states, steps, and transitions.

Useful for:

- approvals
- validations
- multi-step execution
- controlled state changes

Not yet chosen as a primary framing.

## Concepts Clarified

### Workflow

A workflow is a governed sequence of steps through which an intention or process moves.

Example shape for this problem:

- choose ticket
- plan
- implement
- validate
- approve commit
- approve push
- approve PR

Key point:

A workflow is not the whole domain. It is the operational path that something follows.

### Internal Domain Boundaries

A boundary is a responsibility limit inside the system.

Examples mentioned conceptually:

- Tickets
- Planning
- Workspace
- Git Actions
- Approvals

The purpose of a boundary is to stop unrelated responsibilities from leaking into each other.

## What Was Intentionally Deferred

These areas were intentionally left aside for now:

- persistence
- memories
- distributed infrastructure
- event buses outside the app
- cloud concerns

## Open Questions

These questions remain open:

1. What exactly should the rails be: technical capabilities, control surfaces, or movement contracts between parts?
2. How much authority should the center have over the shell?
3. Which internal organization of the shell feels most natural: layers, features, modules, or some blend?
4. Which concerns belong to the architectural core versus later adaptive subsystems?
